Работаем над готовым прототипом, не переписываем с нуля. Источник истины: официальное ТЗ и source pack команды; устные пожелания второстепенны. Язык общения и интерфейса: русский. Не выдумывать факты о заказчике; разделять подтверждённое, гипотезы и предположения.

## Запуск и тесты
```bash
cd app
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env            # заполнить локально, .env в git не попадает
.venv/bin/python -m pytest -q   # должно быть 25 passed
.venv/bin/python -m uvicorn backend.main:app --port 8000   # http://localhost:8000
```
Подробности: `app/README.md`. Живой аудит стенда: `.venv/bin/python scripts/audit_live.py <URL>`.

## Структура
- `app/backend/` FastAPI + SQLite (`main.py` API, `preflight.py` проверки и автомакет, `imagegen.py` локальная генерация, `db.py`).
- `app/frontend/` статический фронтенд без сборки: `app.js` (логика и экраны), `styles.css` + `design.css` (оформление v3/v2), `motion.js`.
- `app/tests/test_api.py` тесты API. `docs/` документация (аудит `08-audit.md`, решения `DECISIONS.md`).

## Координация перед каждой задачей (обязательно, 3 команды)
Чтобы не править одни и те же файлы одновременно, команда и агенты общаются через репозиторий (`.team/`, скрипт `tools/team.py`, только Python 3, без зависимостей). Имена: `sasha` (Claude, Саша) и `kent` (Codex, Кент); у остальных своё короткое имя.
1. **Перед началом работы** прочитать: `python3 tools/team.py status` (кто что занял) и `python3 tools/team.py inbox <своё_имя>` (сообщения).
2. **Занять файлы:** `python3 tools/team.py start <имя> "<что делаю>" <файл-или-папка>...`. Если ответ «ЗАНЯТО», не править эти файлы: выбрать другую задачу или написать коллеге `python3 tools/team.py say <от> <кому> "<текст>"`.
3. Работать в своей ветке `feature/<кратко>`, перед пушем тесты (`cd app && .venv/bin/python -m pytest -q`), в `main` через Pull Request.
4. **После работы** (PR слит или работа остановлена): `python3 tools/team.py finish <имя>`. Заявка без обновления 4 часа считается устаревшей.
Эта же процедура касается задач из `docs/TEAM.md`: доска описывает ЧТО делать, заявки в `.team/` показывают, КТО СЕЙЧАС правит какие файлы.

## Правила
1. Перед правками и перед пушем прогонять тесты. Новая логика бэкенда без теста не принимается.
2. Работать в своей ветке (`feature/<кратко>`), в `main` только через Pull Request. Мелкие коммиты, понятные сообщения по-русски.
3. Не коммитить секреты, `.env`, `app/data/`, токены, пароли, реальные персональные данные, материалы заказчика (PDF/DOCX). Данные только синтетические.
4. Не менять то, что задачей не затронуто. Крупные изменения (архитектура, схема БД, дизайн всего приложения) сначала согласовать в `docs/TEAM.md`.
5. Файлы-«горячие точки» (`app/frontend/app.js`, `app/backend/main.py`, `design.css`): перед началом работы пометить в `docs/TEAM.md`, кто их правит, чтобы не было конфликтов слияния.
6. Не выдавать непроверенное за готовое: статусы PASS/FAIL/UNKNOWN вести честно в `docs/08-audit.md`.
7. Всё бесплатное и с открытыми лицензиями; новые зависимости и модели вносить в `docs/09-licenses.md`.
8. Приоритет: обязательный путь по ТЗ (фото → автомакет → правки → проверка → TEST-заказ → статус), затем «изюминка».
