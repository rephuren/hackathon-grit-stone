## Что сделать

### Данные (УП-01)
`pulse_data.py` создаёт таблицы `pulse_*` в той же SQLite и заполняет их детерминированно (фиксированный seed), если пусто. Минимум три источника, связанные общими id:
1. **Продажи/заказы** — реальная таблица `orders` (наши TEST-заказы) + синтетическая история заказов за ~12 недель (`pulse_orders`: id, дата, продукт, канал, сегмент, сумма в BYN, статус, срок/факт).
2. **Производство** — `pulse_production` (order_id → смена, участок, план/факт выпуска, брак/перепечатка, простой).
3. **Финансы** — `pulse_finance` (неделя, подразделение, план/факт выручки, себестоимость).
4. (желательно) **Персонал** — `pulse_staff` (подразделение, штат план/факт, отсутствия).

Подразделения: `sales` (продажи), `production` (производство), `finance` (финансы). В каждой записи явно `source` и `updated_at` (с часовым поясом). Деньги — с валютой (BYN).

Реальное и mock различать: в ответе API у каждого KPI поле `data: "real" | "synthetic"`.

### KPI (УП-02)
Не менее 10, каждый с `formula`, `source`, `updated_at`, `plan`, `fact`, `status` (green/yellow/red), `dept`. Например: оборот, валовая маржа, заказы в срок, доля брака/перепечаток, новые клиенты, средний чек, конверсия воронки (из реальной таблицы `events`), очередь производства, lead time, загрузка мощности, обеспеченность персоналом, SLA поддержки (из `tickets`).

### Фильтр и детализация (УП-03)
`GET /api/pulse/kpi?period=&dept=&product=` — фильтр меняет все связанные показатели.
`GET /api/pulse/kpi/{code}/drill?…` — детализация до подразделения → продукта → заказов и **объяснение хотя бы одного красного отклонения** (например, брак вырос из-за одного участка/смены — заложить это в синтетику).

### Реестр решений (УП-04)
Таблица `pulse_decisions`: проблема, KPI, влияние, причина, действие, владелец, срок, приоритет, статус, dept, created_at/updated_at. Плюс `pulse_decision_log` (история изменений).
`POST /api/pulse/decisions`, `PATCH /api/pulse/decisions/{id}`, `GET /api/pulse/decisions?status=&dept=`. Каждое изменение пишется и в `pulse_decision_log`, и в общий журнал `audit` (`D.audit(...)`).
Сценарий тимлида: отклонение → детализация → причина → действие с ответственным → сохранение → проверка результата (статус «проверено» + пересчёт KPI).

### Роли и права (УП-05, ОТ-02)
Роли в `users.role`: `director` (видит всё), `dept_head` (видит только своё подразделение), `analyst` (видит всё + свежесть источников), существующий `operator` — как analyst.
Подразделение руководителя — в `pulse_data` (таблица `pulse_user_dept(user_id, dept)`), чтобы не менять схему `users`.
Проверка прав **на сервере**: клиент (`client`) получает 403 на любой `/api/pulse/*`; `dept_head` получает 403 / отфильтрованные данные по чужому подразделению. Отказы — в `audit` с `result="denied"`.
Тестовые пользователи — по образцу `db.init_db()` (только при `SEED_TEST_USERS=1`, тестовый пароль, создаются, если логина нет), но код посева в `pulse.init()`: `director`, `head_sales`, `head_prod`, `analyst`.

### Интерфейс
Отдельная страница `app/frontend/pulse.html` (+ `pulse.js`, `pulse.css`), десктоп и планшет в первую очередь, адаптивно до 390 px. Вход — тот же `POST /api/auth/login`, токен — `localStorage.pp_token`. Ванильный JS без сборки, цвета из брендбука (жёлтый #FFDA00-ряд, токены из `app/frontend/design.css`).
Экраны: «Пульс» (карточки KPI с план/факт/статус, фильтры), детализация KPI, «Реестр решений» (фильтры, карточка, история), для analyst — «Источники» (свежесть, пропуски/дубли).
